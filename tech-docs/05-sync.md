# 5. Синхронизация и облако

Облако необязательно. Пока `config.js` не заполнен (или в режиме тестов), данные живут только на устройстве.

## Конфигурация

`config.js` задаёт `window.HABIT_CONFIG`:
- `supabaseUrl` — адрес проекта `https://<id>.supabase.co`;
- `supabaseKey` — публичный ключ (`anon` / `publishable`). Ключ `service_role` сюда класть нельзя;
- `vapidPublicKey` — публичный ключ для Web Push.

Синхронизация включается, только если адрес похож на Supabase и ключ длиннее 20 символов.

## Вход

- Пользователь вводит почту. `signInWithOtp` отправляет письмо со ссылкой и шестизначным кодом.
- Вход возможен по ссылке или вводом кода (`verifyOtp`). Код удобен в установленном PWA, где ссылка открылась бы в браузере.
- Сессия хранится библиотекой Supabase и обновляется автоматически. Токен из адреса сразу убирается (`history.replaceState`).
- Если на устройство входит другой пользователь, локальные данные прошлого пользователя заменяются пустым состоянием (`OWNER_STORE`).

## Таблица `habit_data`

| Колонка | Тип | Смысл |
|---|---|---|
| `user_id` | uuid, PK, → `auth.users` | Владелец |
| `data` | jsonb | Всё состояние `state` |
| `version` | bigint | Номер версии для оптимистичной блокировки |
| `updated_at` | timestamptz | Время изменения |

RLS: каждый видит и меняет только свою строку. Триггер ограничивает размер `data` 5 МБ.

## Алгоритм синхронизации

На устройстве хранится **база** (`-sync-base`): последняя версия, которая точно совпадала с облаком, и её номер.

**Отправка (`cloudPush`)**
1. Если состояние равно базе — отправлять нечего.
2. Нет записи в облаке — `insert` с версией 1.
3. Иначе — `update ... where version = база.version` с версией +1. Если строка обновилась, база сдвигается.
4. Если версия в облаке уже другая (обновило другое устройство), выполняется `cloudPull` и попытка повторяется, до 4 раз.

**Получение (`cloudPull`)**
1. Читается строка из облака.
2. Если версия совпадает с базой — ничего не меняется.
3. Иначе выполняется **трёхстороннее слияние** `mergeStates(база, локальное, облачное)`, результат нормализуется, применяется и становится новой базой.

**Трёхстороннее слияние**
- Списки с id (привычки, категории, задачи, списки задач, цели): по каждой записи берётся изменённая сторона. Если изменены обе — побеждает более позднее `updatedAt`, а у задач и целей поля сливаются по отдельности.
- Дневные карты (`log`, `skip`, `notes`): слияние по дням и привычкам. Изменения с разных устройств в разные дни не мешают друг другу.
- Одиночные объекты (`profile`, `smart`, `goalRemind`): если локально не менялось — берётся облачное.
- Удаление на одной стороне сохраняется, если другая сторона эту запись не меняла.

**Когда запускается**
- После каждого `save()` — отправка с задержкой (очередь).
- При запуске и при возвращении в приложение — `cloudCheck` сверяет версии.
- Realtime: подписка на изменения своей строки; чужая версия запускает `cloudSync`.
- При ошибке сети — повтор через 15 с (онлайн) или 60 с (офлайн). Ошибка размера показывает предупреждение один раз.

## Общие списки

Отдельные таблицы, доступ только участникам:

| Таблица | Смысл |
|---|---|
| `shared_lists` | Список: владелец, название (до 40) |
| `shared_members` | Участники и их имена (до 24); до 5 участников, до 10 списков у пользователя |
| `shared_items` | Записи (до 200 символов, до 500 в списке), кто добавил и кто отметил |
| `shared_invites` | Коды приглашений со сроком и числом использований |
| `shared_join_log` | Журнал вступлений для ограничения частоты |

Действия, которые нельзя выразить простыми правами, выполняются функциями `create_shared_list`, `create_invite`, `join_shared_list`, `leave_shared_list`, `remove_shared_member`. Триггеры-сторожа запрещают менять владельца, список записи, автора и служебные даты, а также ставят «кто отметил» сами.

На устройстве хранится офлайн-копия общих списков: без сети они показываются с пометкой «Нет сети».

## Удаление аккаунта

Функция `delete_my_account()` (security definer) удаляет пользователя из `auth.users`. Каскадом удаляются его данные, подписки на уведомления и его общие списки. В чужих списках его записи остаются без автора. В приложении можно дополнительно стереть локальные данные.

## Файлы сервера

| Файл | Назначение |
|---|---|
| `supabase-setup.sql` | Таблица `habit_data` и RLS |
| `supabase-size-limit.sql` | Ограничение размера записи |
| `supabase-push.sql` | Подписки на уведомления и журнал отправок |
| `supabase-shared-lists.sql` (+ `-test.sql`) | Общие списки и их проверка |
| `supabase-delete-account.sql` | Удаление аккаунта |
| `supabase/functions/send-reminders/index.ts` | Серверная функция напоминаний |

Все SQL-файлы можно запускать повторно: объекты создаются, если их нет, а функции и политики пересоздаются.
