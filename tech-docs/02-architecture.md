# 2. Архитектура

## Общая схема

```
┌──────────────────────────── Браузер / PWA ────────────────────────────┐
│ index.html ── styles.css                                              │
│     │                                                                 │
│  app.js (точка входа) ──► js/*.js (ES-модули)                         │
│     │                        │                                        │
│     │        ┌───────────────┼──────────────────────┐                 │
│     │     Интерфейс       Состояние              Облако               │
│     │   render, form,    storage.js ◄──► sync.js ─────► Supabase     │
│     │   tasksui, ...     (state, save)   push.js ─────► Web Push     │
│     │                        │                                        │
│     │                  localStorage                                   │
│  sw.js ── Cache Storage (офлайн-оболочка)                             │
└───────────────────────────────────────────────────────────────────────┘
```

## Слои

1. **Ядро** (`core.js`, `icons.js`): константы, даты, ключи хранилища, настройки устройства, иконки. Ни от чего не зависит.
2. **Состояние** (`storage.js`, `tasks.js`, `goals.js`, `plan.js`, `repeat.js`): единый объект `state`, его нормализация, сохранение и чистые функции расчёта (серии, выполнение плана, повторы, группировка задач).
3. **Интерфейс** (`ui.js`, `render.js`, `form.js`, `history.js`, `summary.js`, `tasksui.js`, `goalsui.js`, `settings.js`, `tabs.js`, `tips.js`, `guide.js`, `lock.js`, `sharedui.js`): построение разметки, обработка событий, окна и меню.
4. **Облако** (`sync.js`, `push.js`, `shared.js`): вход, синхронизация, подписка на уведомления, общие списки.

Чистые функции расчёта не трогают DOM, поэтому их проверяют тесты без интерфейса.

## Поток данных

1. Пользователь действует (касание, жест, ввод).
2. Обработчик меняет `state` и ставит `updatedAt` изменённой записи.
3. Вызывается `save()`: состояние пишется в `localStorage` и ставится в очередь синхронизации.
4. Вызывается перерисовка затронутой части (`render()`, `renderTasks()` и т.д.). Перерисовка точечная: блоки сравнивают новый HTML с прошлым и не трогают DOM без изменений.
5. Если включено облако, `sync.js` отправляет состояние в Supabase с проверкой версии (оптимистичная блокировка). Изменения с других устройств приходят через Realtime, сливаются и применяются.

## Запуск

1. `index.html` загружает `config.js` (адрес Supabase и публичные ключи) и `app.js` как модуль. Для старых браузеров есть `legacy.js` с сообщением «браузер устарел».
2. `app.js` импортирует все модули, проверяет, не встроено ли приложение в чужой сайт, загружает состояние (`load()` → `normalize()`), применяет тему и рисует главный экран.
3. После первой отрисовки проверяется шрифт эмодзи, регистрируется service worker, при наличии сохранённого входа поднимается облако.
4. Режим тестов (`?test`) включает отдельное пространство имён хранилища, отключает облако и уведомления и выставляет экспорты модулей в `window`.

## Офлайн-режим (Service Worker)

| Запрос | Стратегия |
|---|---|
| Навигация на корень / `index.html` | Сначала сеть, копия в кэш; без сети — из кэша |
| `config.js` | Сначала сеть без кэша; без сети — копия или пустая конфигурация |
| Свои файлы, Google Fonts, библиотека Supabase | Сначала кэш, затем сеть с сохранением |
| `tests/`, `*.ts`, `sw.js` | Не кэшируются |

- Кэши именуются по версии (`shell-3.4`, `runtime-3.4`). При активации новой версии старые кэши удаляются.
- Оболочка (`SHELL_FILES`) — все модули, стили, иконки и заставки — скачивается при установке.
- На `localhost` service worker сам себя снимает и чистит кэши, чтобы разработка шла без кэша.
- Service worker также принимает push-сообщения и открывает приложение по нажатию на уведомление.

## Версионирование файлов

Каждый модуль и стили подключаются с меткой `?v=3.4`. Метка должна совпадать во всех местах (`sw.js`, `index.html`, `app.js`, все `import` в `js/`). Иначе установленное приложение может смешать старые и новые файлы. Совпадение проверяет тест «all modules loaded with app version».
