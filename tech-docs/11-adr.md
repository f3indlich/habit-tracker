# 11. Журнал архитектурных решений (ADR)

Формат: контекст → решение → последствия. Статус всех записей — «принято».

## ADR-1. Статический сайт без сборки

**Контекст.** Приложение ведёт один владелец, развёртывание — GitHub Pages.
**Решение.** Чистые HTML, CSS и ES-модули без сборщика, транспиляции и npm-зависимостей в рантайме.
**Последствия.** Нулевая настройка, любой файл можно открыть и править напрямую, отладка без исходных карт. Взамен версия ставится вручную меткой `?v=` во всех импортах, а проверку типов и минификацию не используем.

## ADR-2. Единый объект состояния

**Контекст.** Нужны офлайн-работа и простая синхронизация.
**Решение.** Всё состояние — один JSON в `localStorage` и одна строка `habit_data` в облаке.
**Последствия.** Простое сохранение, экспорт и импорт одним файлом, слияние целиком. Ограничения — около 5 МБ на устройстве и 5 МБ в облаке; при росте данных понадобится IndexedDB и разбиение по сущностям.

## ADR-3. Нормализация на входе

**Контекст.** Данные приходят из разных версий приложения, импорта и других устройств.
**Решение.** Любые данные проходят `normalize()` перед использованием.
**Последствия.** Остальной код доверяет формату и не проверяет поля. Новое поле обязательно добавляется в нормализацию.

## ADR-4. Трёхстороннее слияние с оптимистичной блокировкой

**Контекст.** Одним аккаунтом пользуются с нескольких устройств, в том числе офлайн.
**Решение.** Запись с проверкой версии; при конфликте — слияние «база / локальное / облачное» по записям и по дням.
**Последствия.** Правки с разных устройств не теряются. Последним словом при одновременной правке одной записи становится более позднее `updatedAt`.

## ADR-5. Supabase как облако

**Контекст.** Нужны вход без пароля, база с правами на уровне строк, реальное время и серверные функции без своего сервера.
**Решение.** Supabase (Postgres + RLS, Auth, Realtime, Edge Functions). Библиотека грузится лениво и только при включённой синхронизации.
**Последствия.** Безопасность обеспечивают политики RLS, приложение использует только публичный ключ. Без облака приложение полностью работает.

## ADR-6. Web Push через серверную функцию по расписанию

**Контекст.** Напоминания должны приходить при закрытом приложении.
**Решение.** Подписки в базе, функция по `pg_cron` каждые 5 минут, защита от повторов через `push_log`.
**Последствия.** Точность до 5 минут, на iPhone только у установленного приложения.

## ADR-7. Собственный тестовый стенд в браузере

**Контекст.** Приложение без сборки; нужны проверки реального DOM, жестов и вёрстки.
**Решение.** Тесты выполняются в настоящем браузере внутри фрейма; запуск через CDP (Edge/Chrome) и Playwright (WebKit).
**Последствия.** Тесты видят ровно то, что пользователь, включая вёрстку и CSP. Нет зависимостей в самом приложении.

## ADR-8. Принципы интерфейса

**Контекст.** Основное устройство — iPhone; приложение открывают много раз в день.
**Решение.** Статичная вёрстка, «отключать, а не скрывать», цели касания 44 px, одна точка входа «+» для создания.
**Последствия.** Интерфейс предсказуем, но каждое новое действие требует места в уже зарезервированной сетке.

## ADR-9. «Личное» — замок, а не шифрование

**Контекст.** Нужно скрыть часть записей от посторонних глаз на телефоне.
**Решение.** PIN (PBKDF2) скрывает личные записи в интерфейсе и в уведомлениях; данные не шифруются.
**Последствия.** Просто и надёжно для бытового сценария, синхронизация и слияние работают как обычно. От человека с доступом к хранилищу или аккаунту не защищает.

## ADR-10. Implicit-поток входа

**Контекст.** Вход по ссылке и коду из письма в PWA.
**Решение.** Используется implicit-поток Supabase; токен сразу удаляется из адреса. Переход на PKCE владелец отложил.
**Последствия.** Работает во всех сценариях, включая установленное приложение; риск утечки токена через адрес минимизирован, но не исключён полностью.
